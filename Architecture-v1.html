SnakePlanning Architecture

Physicians load a CT scan and a 3D lung model, then plan a route to a cancerous lesion.

The CT is a NIfTI study. The lung model is the airway meshes. A point chosen in that model becomes a path through the lumen, and the plan keeps the path as a named target. Playback flies the endoscope along the route that was just planned.

The wxWidgets shell owns windows and menus. BronchoController owns the plan, the camera, and the active route. BronchoEngine builds that route from the meshes. BronchoView draws the model, the path, and the CT slices.

Scroll, or click a section on the left. Play the planning demo.

Section 1

Software components

The same workspace runs two ways. main.cpp opens BronchoAppFrame, and that frame fills itself with one BronchoPanel. That is the standalone application. Another application skips the frame and parents BronchoPanel in its own window. The panel is the planning surface either way: canvas, plan menu, targets, and playback.

A parent window never calls VTK pathfinding, and the engine never opens a dialog. The controller is the only type both sides know.

The panel sends commands in. The controller asks the engine for a route, writes poses into the view, and keeps the plan and the CT offset. Tests construct the engine and the controller with an off-screen render window and never open the frame.

Section 2

Why the split is worth it

Changing one layer does not affect the others. Updated controls do not affect routing logic. A better lumen search does not repaint the buttons. A new marker does not change what a mouse click means.

Model

BronchoEngine answers geometry questions: load these shells, is this point inside the airway, what track joins these two points. PatientPlan and CTVolume are data. None of them know about wx widgets.

View

BronchoView places renderers, shells, the catheter, and the CT strip. It receives a TrackPoint list and an index. It does not decide where the endoscope is allowed to go.

Controller

BronchoController is the policy. A map click becomes a route. Playback advances one sample. A saved target is committed onto the plan. The panel and the canvas both call this type, so they share one route.

Each component can be tested separately

  • Route tests run headless. They load an STL, call ComputeRoute, and check positions and view-up. No frame, no timer.
  • The panel can show a progress dialog while LoadAirways reports a step name and a percent. The engine does not know the dialog exists.
  • The CT strip can be shown or hidden by telling the view to relayout. Alignment stays on the controller, next to the volume it owns.

What the split prevents

  • Path math buried in a mouse handler, where a horizon fix would also risk the file dialogs.
  • Two copies of the active route, one in the list box and one in the camera.
  • A view that both draws the catheter and decides how far a reverse fly may retract.
Section 3

One gesture, three layers

The anatomy map and the fly-by view are both interactive, and each one answers the pointer in its own way. On the map, a drag orbits the model and a short click jumps to that airway point. In the fly-by view, a drag looks around in place. The panel owns that mouse handler: it sees which view was touched and forwards the command. The decision lives on the controller. The geometry lives on the engine. The picture lives on the view.

Playback is the same shape. The panel timer calls Tick(). The controller steps along m_ActiveRoute and asks the view to redraw the catheter behind the camera. The engine is idle until the next jump or load.

Section 4

Controller interface

BronchoController.h. The panel and the canvas call these. They do not reach into the engine.

Initialization takes the canvas render window and an airway folder. Later loads report progress with a callback so the panel can paint a bar without the controller knowing it is a dialog.

JumpToAirwayPoint is the map. Near the tracheal inlet it restores the look-down entry pose. Anywhere else it builds a route and stops short of the wall.

FreeFly moves along the airway. A negative distance retracts along the catheter polyline. LookDrag yaws and pitches in place. Tick is one playback step, driven by the panel timer.

class BronchoController {
public:
    void Initialize(vtkRenderWindow* renWin,
                    const std::string& dataPath);

    void LoadNewModel(
        const std::string& dataPath,
        const std::function<void(const std::string&, int)>&
            onProgress = {});

    void JumpToAirwayPoint(const double dest[3],
                           bool isTarget);
    void FreeFly(double distance);
    void LookDrag(double yawDeg, double pitchDeg);
    void Tick();

    bool LoadCT(const std::string& path, /* onProgress */);
    bool LoadPlan(const std::string& filePath,
                  /* onProgress */);
    void CommitCurrentTarget(const std::string& name);

    const std::vector<TrackPoint>& GetActiveRoute() const;

private:
    std::unique_ptr<BronchoEngine> m_Engine;
    std::unique_ptr<BronchoView>   m_View;
    CTVolume                        m_CTVolume;
    PatientPlan                     m_ActivePlan;
    std::vector<TrackPoint>         m_ActiveRoute;
};
Section 5

Engine interface

BronchoEngine.h. Coordinates in, a track out. The lumen grid stays private.

LoadAirways reads every STL, builds the shells used for drawing, and voxelises a watertight lumen. The progress callback is optional, so tests omit it.

ComputeRoute returns an empty track when the two points are not connected inside the airway. Callers trim and aim that track with the two static helpers. IsMoveValid is the wall check for a candidate camera position.

LumenField is only a forward declaration here. Routing code in the cpp sees the voxels. Everyone else sees SampleLumenPoints or a finished TrackPoint list.

Section 6

View interface and the shared pose

BronchoTypes.h and BronchoView.h. The track is the contract between the engine and the picture.

struct TrackPoint {
    double pos[3];     // camera, millimetres
    double focal[3];   // look-at point
    double up[3];      // view-up
};

class BronchoView {
public:
    void Initialize(vtkRenderWindow* renWin);
    void SetupWidgets();
    void SetupMeshes(
        vtkPolyData* visualMesh,
        const std::vector<AirwaySegment>& segments);

    void UpdateBreadcrumbs(
        const std::vector<TrackPoint>& track,
        size_t currentIndex);

    void LayoutRenderers();
    void BuildCTSlices(CTVolume* volume);
    void SetCTVisible(bool visible);

    vtkRenderer* GetLeftRenderer() const;   // map
    vtkRenderer* GetRightRenderer() const;  // endoscope
};

TrackPoint is the whole pose. Position, look-at, and view-up travel together so a saved target can restore the camera later.

UpdateBreadcrumbs draws the path still ahead of currentIndex and the catheter behind it. The tube ends short of the camera so the endoscope view stays clear of the shaft.

BuildCTSlices borrows a CTVolume owned by the controller. The view lays axial, coronal, and sagittal panels under the 3D views and moves only the slice planes when the endoscope moves. Framing stays fixed to the study bounds.

GetRightRenderer is how the canvas tells a left-drag in the endoscope apart from a left-drag on the map. The map orbits. The endoscope looks in place.

Section 7

From STL files to a camera track

Loading makes two products from the same shells. One is drawn. One is searched. The search prefers the voxelised lumen. A surface geodesic is the fallback when the shells are not watertight enough to voxelise.

After the centreline exists, headings are smoothed and view-up is carried along the path. That last step is ApplyStableViewUp. It is what keeps a branch entry from rolling the horizon in one frame.

Section 8

Engine View Example

ApplyStableViewUp in BronchoEngine.cpp writes the up vector of every sample. It parallel-transports the previous up onto the new look direction, then rolls toward a level horizon by at most 0.55 degrees per sample. Looking straight down a trachea, world Z is almost the look axis, so the roll waits until the airway turns and a horizon exists.

void ApplyStableViewUp(std::vector<TrackPoint>& track)
{
    if (track.empty())
        return;

    auto ForwardOf = [](const TrackPoint& tp, double fwd[3]) {
        fwd[0] = tp.focal[0] - tp.pos[0];
        fwd[1] = tp.focal[1] - tp.pos[1];
        fwd[2] = tp.focal[2] - tp.pos[2];
        return Normalize3(fwd);
    };

    // Level up is world +Z with the look direction removed.
    // Skip it when the airway is nearly vertical: there is no horizon yet.
    auto GravityUp = [](const double fwd[3], const double prevUp[3], double out[3]) {
        double worldZ[3] = { 0.0, 0.0, 1.0 };
        double right[3];
        vtkMath::Cross(fwd, worldZ, right);
        if (vtkMath::Norm(right) < 0.12)
            return false;
        double level[3] = { worldZ[0], worldZ[1], worldZ[2] };
        SubtractTangent(level, fwd);
        if (!Normalize3(level))
            return false;
        if (vtkMath::Dot(level, prevUp) < 0.0) {
            level[0] = -level[0];
            level[1] = -level[1];
            level[2] = -level[2];
        }
        Copy3(level, out);
        return true;
    };

    // Roll `up` toward `desired` around the look axis, capped at maxRad.
    auto RollToward = [](double up[3], const double fwd[3],
                         const double desired[3], double maxRad) {
        double a[3] = { up[0], up[1], up[2] };
        SubtractTangent(a, fwd);
        if (!Normalize3(a))
            return;
        double b[3] = { desired[0], desired[1], desired[2] };
        SubtractTangent(b, fwd);
        if (!Normalize3(b))
            return;
        double cross[3];
        vtkMath::Cross(a, b, cross);
        const double err = std::atan2(vtkMath::Dot(fwd, cross), vtkMath::Dot(a, b));
        const double step = std::max(-maxRad, std::min(maxRad, err));
        RotateAbout(a, fwd, step);
        SubtractTangent(a, fwd);
        if (Normalize3(a))
            Copy3(a, up);
    };

    double prevFwd[3] = { 0.0, 0.0, -1.0 };
    ForwardOf(track.front(), prevFwd);
    double up[3] = { 0.0, 1.0, 0.0 };
    double gravity[3];
    if (GravityUp(prevFwd, up, gravity))
        Copy3(gravity, up);
    Copy3(up, track.front().up);

    constexpr double kMaxRollDeg = 0.55;

    for (std::size_t i = 1; i < track.size(); ++i) {
        double fwd[3];
        if (!ForwardOf(track[i], fwd))
            Copy3(prevFwd, fwd);

        // Carry the previous up onto the new heading.
        double transported[3] = { up[0], up[1], up[2] };
        double axis[3];
        vtkMath::Cross(prevFwd, fwd, axis);
        const double sinAngle = vtkMath::Norm(axis);
        if (sinAngle > 1e-9) {
            axis[0] /= sinAngle; axis[1] /= sinAngle; axis[2] /= sinAngle;
            RotateAbout(transported, axis,
                std::atan2(sinAngle, vtkMath::Dot(prevFwd, fwd)));
        }
        SubtractTangent(transported, fwd);
        Normalize3(transported);
        Copy3(transported, up);

        if (GravityUp(fwd, up, gravity))
            RollToward(up, fwd, gravity, vtkMath::RadiansFromDegrees(kMaxRollDeg));

        SubtractTangent(up, fwd);
        Normalize3(up);
        Copy3(up, track[i].up);
        Copy3(fwd, prevFwd);
    }
}

The source function keeps a few extra fallbacks when a vector will not normalize. The shape above is the algorithm: transport, then a capped roll. A test walks a three-generation tree and requires each sample's up to change by less than 0.6 degrees. The annotated source is in the Doxygen page for BronchoEngine.cpp.

Section 9

SuperBuild and the submodule

SnakeNavigation is a git submodule of SnakeLibrary. The Canon SuperBuild compiles that submodule inside the host tree. SnakePlanning can also configure itself and pull the same kinds of libraries with vcpkg.

Canon SuperBuild

The first CMake pass on SnakeLibrary has Snake_SUPERBUILD on, so it includes SuperBuild.cmake and returns. That file clones each dependency with ExternalProject_Add and a shallow git tag, builds it, and installs it under build/<name>-proj. A second external project then configures this same source tree with Snake_SUPERBUILD off. Its binary directory is build/SnakeLibrary.

Later configures leave EP_UPDATE_DISCONNECTED set, so those clones stay put. OpenSSL is skipped when OPENSSL_ROOT_DIR is already set. GoogleTest is added when BUILD_TESTING is on.

  • SnakeNavigation/CMakeLists.txt is the piece that FetchContent-clones VTK. While that configure runs, find_package(wxWidgets) is disabled so VTK cannot replace the Canon include paths. It is turned back on before SnakePlanning is added.
  • SnakePlanning sees VTK::CommonCore already defined, so it does not call find_package(VTK). wxWidgets comes from the SuperBuild install. The host asked for base, xml, core, html, media, and xrc; the canvas also links the wxgl target.
  • The test target uses the SuperBuild gtest targets. A second FetchContent of googletest would collide with those names, so the tests fetch GoogleTest only when no gtest target exists yet.
  • Runtime DLLs for wx, VTK (_deps/vtk-build/bin), and GoogleTest are copied next to the executables, along with airway_segments. The app lands in build/SnakeLibrary/Release.

Submodule on its own

SnakePlanning/build_and_run.ps1 treats this folder as the top-level project. It bootstraps a local vcpkg, installs the three libraries the app needs, and passes that toolchain into CMake. The x64-windows triplet is release-only, which matches the Release configuration this standalone project generates.

  • vcpkg lives in SnakePlanning/vcpkg. CMake receives scripts/buildsystems/vcpkg.cmake on the command line for this configure, so those libraries stay with this build.
  • The libaec port is rewritten to download from GitHub before vcpkg install runs. Install is retried when a download fails.
  • As the top-level project, SnakePlanning calls find_package for VTK and wxWidgets. Tests use the vcpkg GoogleTest. FetchContent of googletest v1.14.0 runs only if that package is missing.
  • When BUILD_RCS_NAVIGATION is on, the submodule looks for LibTorch at LIBTORCH_ROOT, C:/libtorch, or the torch package on PYTHON. That path is a local install.
